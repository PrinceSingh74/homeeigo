# PHASE 15 — Test Isolation Incident

**I ran the test suite against the production database. This is what happened, what it wrote, and
what now prevents it.**

Reported in full rather than folded into a regression table, because the standing instruction on
this project is that production must not be mutated, and it was.

---

## A. What happened

At 22:30 IST on 2026-09-05 I launched the full backend regression. The command chain's working
directory was the **repo root** (`D:\homigo`) rather than `apps/backend`.

The test-database isolation for this project lives in `apps/backend/bunfig.toml`:

```toml
[test]
preload = ["./src/load-env.ts", "./src/__tests__/helpers/keep-shared-prisma-alive.ts"]
```

`bunfig.toml` is resolved from the **working directory**. From the repo root there is none, so:

1. `load-env.ts` never ran.
2. `.env.test` was never loaded, so `DATABASE_URL` stayed at `.env`'s value — `homigo_db`.
3. `load-env`'s own "refuse unless the database name contains test" guard never ran either, because
   it lives *inside* the file that was skipped.
4. Every Prisma client in the process was constructed against **production**.

### Proven, not inferred

The same probe file, same absolute path, only the working directory differing:

```
$ cd apps/backend && bun test .../zz-cwd.test.ts
  injected env (8) from .env.test
  PROBE cwd= D:\homigo\apps\backend   NODE_ENV= test   DB= homigo_test

$ cd D:\homigo     && bun test .../zz-cwd.test.ts
  (no env injection line)
  PROBE cwd= D:\homigo                NODE_ENV= test   DB= homigo_db     <-- PRODUCTION
```

The run logs corroborate it: the bad run printed paths as `apps\backend\src\__tests__\...` with no
`injected env` line; every good run printed `src\__tests__\...` with it.

## B. What it wrote to production

Read-only audit of `homigo_db`:

```
bookings created in the 22:30 hour : 141
  52  "Adv Service adv-ent-ops-mtonpcc3"
  50  "Adv Service adv-chaos-mtonowzh"
  22  "Adv Service adv-soak-mtonphyz"
   4  "Adv Service adv-p03-mtonoq91"
   4  "Adv Service adv-run-mtonolkz"
  ... all remaining are "Adv Service adv-*" fixture services

payments created in the same window : 60
wallet transactions                 : 1
```

Every one is fixture data — the `adv-*` naming is generated by
`src/__tests__/helpers/adversarial-fixtures.ts`. For comparison, the four preceding hours of genuine
activity contain **7 bookings in total**.

**No pre-existing production row was modified or deleted.** The contamination is additive: fixture
rows created alongside real data, not damage to it.

### What limited it

15 test files call `refuseIfNotIsolatedTestDb` and aborted with
`REFUSING TO RUN: connected to homigo_db`. That guard did its job — and it exists in only **15 of
135** files. The other 120 ran normally against production, which is why 615 tests passed before I
noticed anything was wrong.

---

## C. How it was caught

Not by the guard, and not by looking. The run reported **615 pass / 26 fail** where the previous run
had reported **1151 pass / 10 fail**. A pass count that *drops by 536* cannot be explained by the
code changes in between, so I read an actual failure instead of re-running — and the failure text
was the isolation guard naming `homigo_db`.

Had the drop been small, or had those 15 files not carried the guard, the run would have looked
merely flaky.

---

## D. The fix: a barrier that does not depend on how the suite is launched

The existing protection is correct but sits in the wrong place: `load-env` can only refuse if
`load-env` runs. The new check sits at the one point every path must pass through — the moment a
Prisma client is constructed — in `src/lib/prisma-base.ts`:

```ts
function assertTestDatabaseIsolation(url: string): void {
  if (process.env.NODE_ENV !== "test") return;
  const name = new URL(url).pathname.replace(/^\//, "").split("?")[0] ?? "";
  if (/test/i.test(name) || name === "homigo_p39") return;
  throw new Error("REFUSING TO CONSTRUCT A PRISMA CLIENT: ...");
}
```

`NODE_ENV=test` is set by **Bun itself** for `bun test`, independently of any preload, env file or
working directory. That is what makes it usable here: it is true at client-construction time even
when everything else that should have run did not.

`prisma.ts` extends `prisma-base`, so both clients are covered by the one check.

### Verified in both directions

```
from repo root   : error: REFUSING TO CONSTRUCT A PRISMA CLIENT: NODE_ENV=test but
                   DATABASE_URL points at "homigo_db" ...            0 pass / 1 fail
from apps/backend: 52 pass / 0 fail
full regression  : 1998 pass / 0 fail, 0 refusals
```

The failure mode is now loud and immediate instead of silent and productive.

## E. What I have NOT done, and why

**The 141 fixture bookings and 60 payments are still in `homigo_db`.**

Deleting rows from production is exactly the class of action the standing instruction forbids
without explicit authorization, and "I created them by mistake" does not convert a destructive
production write into an authorized one. Cleaning up my own mess unasked would be the same category
of error as the one that made the mess.

They are precisely identifiable:

```sql
-- inspect first
SELECT b.id, s.name, b.created_at
FROM bookings b JOIN services s ON s.id = b.service_id
WHERE s.name LIKE 'Adv Service adv-%'
  AND b.created_at >= '2026-09-05 22:00:00+05:30';
```

Their services, providers and customers are `adv-*` fixtures too, so a full cleanup means removing
the fixture users, services, bookings, payments and the single wallet transaction together, in
dependency order, inside one transaction, after a backup.

**I can do that on request. I will not do it unasked.**

### Side effects worth knowing about while they remain

- 141 fixture bookings and 60 payments are counted by any dashboard that aggregates recent activity
  — GMV, booking volume, conversion — for this period.
- The wallet transaction is one row; ledger integrity was not observed to change.
- Nothing was deleted or overwritten, so removing them restores the prior state exactly.

## F. Honest assessment

The mechanism was documented in the repository before I hit it. `bunfig.toml`'s own comment says:

> `load-env` MUST run before any test file imports prisma — otherwise the first file that skips
> `import "../load-env"` constructs the singleton against .env (homigo_db) and every later file
> inherits that poisoned client.

The author anticipated a *file* skipping the import. Neither of us anticipated the **preload itself**
being skipped, which does the same thing to all 135 files at once. The guard was placed one level
too high, and my working directory found the gap.

Two things follow, and they point in opposite directions:

- The barrier is now at the right level and this specific failure cannot recur.
- **120 of 135 test files still have no isolation guard of their own.** They are now covered by the
  client-construction check, which is a single point — better than before, but still single.
